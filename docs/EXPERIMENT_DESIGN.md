이 문서는 `SCM_LLM_Agent_Harness` revision 4 코드와 seed 201·202·203의 보존된 실행 설정을 기준으로 작성했습니다. 과거 버전 문서의 수치, 기본 클래스 값, 실제 실행에 지정한 값을 구분합니다. 실행 절차는 [README](../README.md), 내부 처리 순서는 [코드 설명](CODE_GUIDE.md), 게시본 검증 근거는 [재현성 기록](REPRODUCIBILITY.md)에 있습니다.

이는 단일 제품·이산 기간·직렬 공급망을 단순화한 실험 환경입니다. 운송 중 물량은 실제로 존재하고 백로그가 상류 미출고를 반영하지만, 생산 자원·다품목·대체 공급처·가격 결정·폐기·긴급 운송·수요의 가격 반응 등은 모델링하지 않습니다. 기간의 현실 단위는 일/주로 고정하지 않았습니다. 비용은 모형 단위이며 API의 USD 비용과 별개입니다.

### OUT 기준량과 안전재고

CMT의 발주 전 재고위치와 기준량은 다음과 같습니다.

```text
IP = I + P_pre - B
Q_base_raw = max(0, forecast_h1 + forecast_h2 + safety_stock - IP)
Q_base = normalize_order(Q_base_raw, cap=100)
```

`Q_base`는 최종 주문을 강제하지 않습니다. LLM은 이를 입력으로 받아 `Q_final`을 별도로 결정합니다. 안전재고 10은 이 목표량에 더하는 수치이며 **항상 재고 10을 보장하는 하한이나 초기 재고가 아닙니다.** A/N0/N0-G0는 평가 단계에 OUT 기준량을 받지 않고, D 두 조건도 CMT의 OUT 식을 사용하지 않습니다. 다만 모든 조건은 SS=10이 적용된 같은 준비기간 상태에서 시작합니다.

## 2. C: 로컬 운영 정보

| 수준 | 상태 관측 | 과거 주문 관측 |
|---|---|---|
| C0 | 현재 포함 10기 D/I/B/P_pre 원자료 | 이전 9기 Q_base·Q_final |
| C1 | 현재 포함 20기 원자료 | 이전 19기 주문 |
| C2 | 현재 포함 5기 원자료 | 이전 4기 주문 |
| C3 | 현재 상태 + 현재 포함 10기의 평균·표본 표준편차·최소·최대 | 이전 9기의 Q_base·Q_final·Q_final−Q_base 요약 통계 |

현재 발주는 아직 결정되지 않았으므로 과거 주문은 상태 기간 수보다 하나 적습니다. C3는 C0와 같은 시간 범위의 가공 표현입니다. 현재 상태는 요약값으로 대체하지 않고 별도로 제공합니다. 구현은 [`scm/harness.py`](../scm/harness.py)의 `build_C()`입니다.

**별도 예측 입력은 모든 CMT에서 자기 수주 최신 30기입니다.** 따라서 C2는 예측까지 5기만 사용하는 조건이 아닙니다. C의 실험 효과는 공통 30기 예측 지원이 있는 상태에서 최종 판단과 방법 선택에 보이는 운영 이력·표현을 바꾼 효과입니다.

## 3. M: 상류로 보내는 추가 정보

| 수준 | 내용 | 생성·전달 |
|---|---|---|
| M0 | 추가 메시지 없음 | 실제 주문 자체는 정상 전달 |
| M1 | 확정 후 I/B/P_post/D, 자기 수주 10기의 평균·표본 표준편차 등 | 환경 코드가 구조화된 숫자 정보 작성 |
| M2 | 이미 확정한 이번 주문의 정성적 이유 | LLM 별도 호출. 정량 수치·통계·미래 주문 계획 제한, 현재 백로그 없음 등의 부재 표현 허용 |
| M3 | t+1·t+2의 자기 발주 계획 정수 두 개 | LLM이 생성. 상세 `planning_evidence`는 연구 로그에만 남김 |
| M4 | 자유 형식 추가 정보 | LLM 별도 호출 |

정보는 즉시 하류→상류 방향으로만 이동합니다. 소매상은 공급망 메시지를 받지 않고 공장은 공급망 메시지를 보내지 않습니다. M2/M4는 받은 내용을 다음 메시지에 반영할 수 있지만 전체 네트워크 상태를 직접 관측하는 것은 아닙니다. M2 문구 검사 통과는 실제 상태와의 의미적 일치나 사실성을 보증하지 않습니다. M3는 미래 실행을 강제하지 않는 계획입니다.

## 4. T: 예측 지원

| 수준 | 방법 결정 | 예측 계산 주체 | 코드 OUT 기준량 |
|---|---|---|---|
| T0 | LLM 자유 예측 | LLM | 제공 |
| T1 | 고정 LR30 공식 | LLM | 제공 |
| T2 | 고정 LR30 | 코드 | 제공 |
| T3 | LLM이 LR30/MA30/SES 중 선택 | LLM | 제공 |
| T4 | LLM이 LR30/MA30/SES 중 선택 | 코드 | 제공 |

예측 대상은 자기 수주의 다음 1기·2기이며 둘 다 연속값으로 유지하고 음수는 0으로 처리합니다. LR30은 절편을 포함한 선형 추세 회귀, MA30은 30기 평균, SES는 α=0.3입니다. SES는 매번 최신 30기 창의 첫 관측에서 초기화하고 그보다 오래된 상태를 이어받지 않습니다. 식은 [`scm/forecasting.py`](../scm/forecasting.py)의 `forecast()`에 있습니다.

계산 위임을 비교하는 기본 대비는 **T1↔T2**, **T3↔T4**입니다. 후자는 각 경로에서 선택 방법 자체도 달라질 수 있어 실제 선택 로그를 함께 봐야 합니다. 코드 계산 아래 방법 선택권은 **T2↔T4**입니다. T0↔T2는 예측 방식과 계산 주체를 동시에 바꾸므로 계산 위임만의 효과로 해석하지 않습니다.

## 5. 등록 조건과 기준조건

등록 조건은 `4 C × 5 M × 5 T = 100`개 CMT와 아래 5개 기준조건으로 **105개**입니다. 전체 목록은 [`configs/registered_conditions.json`](../configs/registered_conditions.json)에 있습니다.

| 조건 | 최종 발주 정보·지원 | 복구·목적 |
|---|---|---|
| A | C0·당기 D로 LLM 직접 발주. M0, 별도 예측과 당기 Q_base 없음 | 일반 상세 프롬프트와 복구. 기본 목적 cost |
| D_cost | C0·M4와 코드 LR30의 **다음 1기 예측값**을 참고량으로 제공 후 LLM 최종 발주 | 목적 cost 고정. CMT OUT 정책과 다름 |
| D_bullwhip | C0·M4와 `sqrt(2 × mean(D_30) × fixed_order_cost / holding_cost)`를 참고량으로 제공 후 LLM 최종 발주 | 목적 bullwhip 고정. EOQ 참고량이 실제 주문을 강제하지 않음 |
| N0 | A와 같은 C0·당기 D 관측, 최소 발주 프롬프트 | 일반 복구, 정보 출처 라벨 제외 |
| N0-G0 | N0와 같은 관측·최소 프롬프트 | 재시도·수량 보정·대체 없는 실행. 첫 복구 가능 호출 오류 또는 부적법 주문에서 해당 에피소드 중단 |

N0-G0에서도 물류의 정수·0~100 제약은 유지합니다. `10`, `10.0`, `1e1`은 같은 적법 정수값으로 허용하지만, 10.5·음수·101·문자열 숫자·불리언 등은 허용하지 않습니다. N0는 하네스가 전혀 없는 자연어 채팅이 아니라, 동일한 실험 환경·구조화 출력·일반 복구를 사용하는 **최소 프롬프트 기준조건**입니다.

기본 CMT·A·N0·N0-G0 목적은 네 단계 합계 운영비 절감이며 `--objective`로 선택할 수 있습니다. D 두 조건의 목적은 고정되어 있어 전체 조건 실행에서는 이를 일괄 변경하지 않습니다. D_bullwhip까지 모두 같은 최적화 목적을 사용했다고 보고하면 안 됩니다.

## 6. 실제 R4 실행과 재현 범위

seed 201·202·203은 같은 R4 런타임 코드·물류 설정·모델 설정으로 실행되었습니다. 보존된 실행 소스와 manifest/summary를 대조한 로컬 감사에서 아래 값을 확인했습니다. 이번 GitHub 게시를 위한 문서 정리는 런타임 코드 개선 실험이 아닙니다.

| 항목 | 확인한 값 |
|---|---|
| 구현 revision | 4 |
| variant | `FINAL_V1_V2_OWNERSHIP_M2_N0` |
| 권장 진입점 | `run_final.py` |
| 런타임 추가 처치 | 100 CMT의 주문 프롬프트에 Q_base=0의 뜻을 명시 |
| SCM 소스 해시 | `e6af3433b1badda8040bf4f39669a3eba3b781da60cb7dba32fcc1009fd136c5` |
| 실제 런타임 해시 | `fd3e7d81a74b3bf45463cb9d2d862cebc1cdf6f8d6f25587ff320b42500ba9b2` |
| 모델 | `google/gemini-2.5-flash-lite` |
| API endpoint | `https://openrouter.ai/api/v1/responses` |
| 요청 provider / tier | `google-ai-studio/flex` / `flex` |
| temperature | 0.1 |
| 최대 출력 | 각 호출 `max_output_tokens=300` |
| timeout / backoff | 60초 / 1초 |
| 일반 조건 재시도 | 논리 작업마다 최대 1회 |

실제 성공 응답의 모델·공급자·service tier를 확인하며, 지정 경로를 검증할 수 없으면 코드가 실행을 멈춥니다. 배포 후 API 서비스에서 이 모델·라우팅 조합의 지원 여부가 달라질 수 있습니다. 코드에 들어 있는 토큰 단가는 예산 관리용 고정 설정이며 현재 시장 가격을 보장하지 않습니다. 실제 비용은 provider 보고값과 보고 누락률을 함께 확인해야 합니다.

수요 seed는 수요와 공통 준비기간을 재현합니다. **LLM 출력의 난수 seed를 고정하는 기능은 없습니다.** 같은 수요 seed와 temperature로 다시 호출해도 같은 주문·메시지·결과를 보장하지 않습니다. 코드 해시가 같다는 것은 실행 논리 일치의 근거이지 모델 서비스의 영구적인 동일성을 보장하는 근거가 아닙니다.

보존된 세 seed의 최종 분석 자료는 105×3=315건 중 완료 313건과 N0-G0 중단 2건(201·202)이었습니다. N0-G0의 203은 완료했습니다. 202의 한 조건은 치명적 API 오류 이후 별도 실행한 최종 완주 결과를 채택했으므로 원자료 분석 시 최초 실패 실행과 최종 채택 실행을 중복 집계하지 않아야 합니다. 이번 소스 배포는 원문 API 로그 전체나 결과 데이터 전체를 포함한다는 의미가 아닙니다.

## 7. 성과 지표와 분석할 때 주의할 점

[`scm/metrics.py`](../scm/metrics.py)의 `summarize()`는 예정된 평가기간 전체에 4개 역할 기록이 있는지 확인합니다. 준비기간 자료로 평가기간 분모를 바꾸거나 부분 실행을 완주처럼 집계하지 않습니다.

| 지표 | 정의·해석 |
|---|---|
| `cost_per_period` | 평가기간 4단계 총 운영비 / 평가기간 수. 에이전트 1개당 비용이 아님 |
| `cost_components_per_period` | 보유·백로그·단위 발주·고정 발주 비용의 4단계 합을 각각 기간 수로 나눔 |
| `retailer_immediate_fill_rate` | 신규 소매 고객 수요 중 같은 기간 충족한 수량 비율. 기존 백로그를 먼저 처리한 뒤 신규 수요 충족량을 계산 |
| `order_cv_i` | 역할별 실제 발주의 표본 표준편차(ddof=1) / 평균. 관측 2개 미만 또는 평균 0이면 정의 불가 |
| `global_bullwhip` | 네 역할의 발주 CV의 곱. 전통적인 수요 대비 주문 분산비와 다른 지표 |
| `mean_absolute_order_adjustment` | 기준량이 존재하는 기록의 `abs(Q_final−Q_base)` 평균 |
| `arithmetic_error_count` | LLM 예측과 지정 코드식의 차이가 1e−8보다 큰 예측 숫자 수. 큰 실무적 오차의 개수와 같지 않음 |
| API 사용량 | 실제 시도 단위로 집계. 재시도 포함. 누락값은 0으로 간주하지 않고 알려진 합계와 보고 비율을 별도 제공 |

비용·즉시 충족률·발주 변동은 서로 다른 목표입니다. 재고가 많으면 비용이 높아도 서비스와 주문 안정성이 좋을 수 있습니다. 비용 절감만으로 전체 성능이 우월하다고 결론 내리지 않습니다. 각 seed에 한 번씩 실행한 세 결과는 수요와 LLM 경로 변동을 완전히 분리하는 반복 설계가 아닙니다. 400개 에이전트-기간 기록을 독립 반복 400개로 취급해서도 안 됩니다.

## 8. 설정의 출처와 변경 이유

이 문서는 **구현과 실행 설정의 설명서**입니다. 위 수치가 어떤 원논문의 수치와 같다고 일괄 주장하지 않습니다. Beer Game 계열과 유사한 직렬 구조·백로그·리드타임이라는 가정만으로 4단계·2기·수요 10/3·주문 상한 100·비용계수 1·안전재고 10이 보편적 표준값이라고 결론 내릴 수 없습니다.

안전재고 10과 Q_base 설명 추가는 코드에서 명시적으로 관리하는 프로젝트 처치입니다. 특히 안전재고의 원논문 대응값이나 해당 수치를 선택한 문헌상 최적성은 이 소스만으로 확인되지 않습니다. 기존 논문과의 동일·변경 여부를 보고할 때는 해당 논문의 원문 위치와 보존된 설계 기록을 따로 인용해야 하며, 확인되지 않은 출처나 변경 동기는 **미확인**으로 남겨야 합니다. 사후 성과를 근거로 당시의 변경 이유를 소급해 작성하면 안 됩니다.

결과 해석에 영향을 줄 수 있는 주요 조건은 안전재고·주문 상한·비용 비율·수요 변동·리드타임·초기/준비 상태·평가 길이와 종료 처리입니다. 현재 데이터는 이들 값을 고정한 C/M/T 비교입니다. 별도의 민감도 분석 없이 다른 공급망에도 동일 효과가 유지된다고 일반화하지 않습니다.
