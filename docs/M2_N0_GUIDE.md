# M2 수정과 N0·N0-G0 설명

적용일: 2026-10-16. 버전: `FINAL_V1_V2_OWNERSHIP_M2_N0` (revision 4).

이 문서는 기존 FINAL 설명서 이후의 변경 내용을 설명합니다. 이전 문서나 기록에 있는 103조건은 당시의 실험 설계입니다. 현재는 기존 100 CMT + A + D_cost + D_bullwhip에 N0·N0-G0를 추가한 105조건을 개별 선택할 수 있습니다. 조건 목록이 늘었다고 자동으로 전체 실험이 실행되지는 않습니다.

## 1. 유지되는 환경

- 4단계 공급망의 기존 (1)~(7) 순차 운영, 리드타임 2, 정수 수주·발주, 동일 비용 정의를 유지합니다.
- 권장 실행은 `run_final.py --safety-stock 10`입니다. 안전재고는 공통 준비기간부터 적용합니다. 초기 실물 재고는 별도 설정이며 기본값 0입니다.
- 준비기간은 1~30기, 평가는 31~130기입니다. 동일 seed·환경 설정의 모든 조건은 같은 준비기간 스냅숏과 외생 고객 수요를 공유합니다.
- CMT의 Q_base 의미 설명 추가도 유지됩니다. A, D_cost, D_bullwhip, N0, N0-G0에는 CMT용 Q_base 설명을 붙이지 않습니다.
- N0·N0-G0는 평가기간에 기준 주문량을 만들지 않으므로 평가기간의 SS를 사용한 OUT 정책도 없습니다. SS=10은 이 두 조건에서 공통 준비기간 상태에 반영됩니다.
- 모델·provider·temperature·최대 출력 토큰은 기존 설정 그대로입니다. 소프트웨어 검사는 mock/가짜 HTTP 응답으로 진행하며, 실제 API 소규모 점검의 범위와 결과는 [최종 배포 점검 기록](FINAL_RELEASE.md)에 별도로 기록합니다.

## 2. M2의 정의와 수정

M2는 **제공된 관측 근거로 이미 확정된 이번 발주를 설명하는 정성 메시지**입니다. 별도 메시지 호출에는 원래 주문 호출의 rationale를 제공하지 않습니다. 따라서 실제 내부 추론을 그대로 전달하거나 원래 의도를 복원하는 메시지라고 주장하지 않습니다.

생성 지시는 다음을 요구합니다.

1. 이번 발주와 관련된 관측 근거 한두 가지와 행동의 관계를 짧게 설명합니다.
2. 자신의 상태와 하류에서 전달받은 설명을 구분하고, 자신의 정보를 하류의 상태라고 바꾸지 않습니다.
3. 없는 관측·의도를 만들어 주문을 정당화하지 않습니다. 근거가 부족하면 그 한계를 인정합니다.
4. 현재형 또는 완료형으로 당기 확정 발주를 설명합니다. 미래 계획·상류에 대한 발주 조언·명시적 수량을 포함하지 않습니다. 다만 ‘백로그가 없다/0이다’처럼 현재 상태나 현재 주문의 부재를 나타내는 표현은 허용합니다. 통계나 미래 계획의 0은 이 예외에 포함하지 않습니다.
5. 모든 I/B/P 상태를 나열하도록 강제하지 않습니다. M1의 정량 상태 목록과 구분합니다.

M2에만 공통 메시지 지시의 `intention` 표현을 제거했습니다. M3의 자율 미래 계획, M4의 자유 메시지 지시는 유지합니다. 메시지 길이 상한과 1회 재시도 후 빈 메시지 처리도 기존 공통 G를 사용합니다.

### 검사 규칙

`scm/m2_validation.py`의 `validate_m2_message()`가 명시적 숫자, 수량을 나타내는 일부 숫자 단어, 알아볼 수 있는 미래 발주 계획·조언 표현을 검사합니다. `I will`이라는 표현만으로 무조건 거절하던 검사를 교체했습니다. 당기 행동인 `I will not place an order with the distributor at this time`은 허용하고, `next period`의 계획은 거절하도록 회귀 사례를 검사합니다.

이 검사는 **제한적 문구 규칙**입니다. 모든 언어·의역·소유 주체·사실 일치 여부를 판정하는 의미 검증기가 아닙니다. 오탐·미탐 가능성이 있으며, 규칙 적발 횟수를 실제 의미 오류 확정 횟수로 쓰지 마세요. 실제 전달률과 함께 주체 오류, 관측과 다른 주장, 주문과 설명의 불일치를 별도 분석해야 합니다.

수정 지점:

- `scm/prompts.py`: `message_instructions(..., level="M2", ...)`
- `scm/m2_validation.py`: M2 문구 검사
- `scm/harness.py`: `_validate_message()`에서 검사 실행, 기존 재시도·메시지 생략 흐름 연결

기존 M2는 seed201 실행의 `results/launches/.../frozen_code`와 기존 결과에 보존되어 있습니다. 수정한 M2가 실제 성과를 개선했다는 결론은 새로운 API 실험으로 확인해야 합니다.

## 3. N0와 N0-G0

두 조건은 동일한 최소 프롬프트, 동일한 C0 관측 항목, 동일한 출력 스키마를 사용합니다. **차이는 복구 정책**입니다.

| 항목 | A | N0 | N0-G0 |
|---|---|---|---|
| C0 + 당기 D | 제공 | 동일 항목 | 동일 항목 |
| 당기 별도 예측·Q_base·M | 없음 | 없음 | 없음 |
| 상세 FINAL 의미·주체 안내 | 제공 | 제외 | 제외 |
| information_sources 입력 라벨 | 제공 | 제외 | 제외 |
| 변수의 중립적 정의·관측 시점·물리 규칙·목적 | 제공 | 유지 | 유지 |
| JSON 출력 형식 | 유지 | 유지 | 유지 |
| 추가 API 시도 | 실패 후 최대 1회 | 실패 후 최대 1회 | 0회 |
| 수량 반올림·범위 제한 | 적용 | 적용 | 적용하지 않음 |
| 최종 실패 시 대체 주문 | 당기 수주량 보정값 | 당기 수주량 보정값 | 없음; 즉시 해당 실행 중단 |

N0·N0-G0도 기본 API 연결·관측 전달·합법 행동 검사·물리 환경은 필요합니다. 따라서 이름은 **최소 프롬프트/최소 실행 인터페이스 기준조건**입니다. N0-G0의 G0는 모든 소프트웨어 검증을 제거한다는 뜻이 아니라 **오류에 대한 수정·재시도·대체 실행이 없음**을 뜻합니다. 예산 상한과 모델 경로 확인은 계속 적용합니다.

C0의 과거 주문 행에는 준비기간에 생성한 과거 Q_base가 포함됩니다. A와의 정보 일치를 위해 이 이력도 보존합니다. 현재 시점의 예측이나 기준량을 새로 제공하는 것은 아닙니다. 두 조건은 같은 초기 입력에서 시작하지만 실제 LLM 결정이 달라지면 이후 공급망 상태와 입력값도 달라집니다.

### N0-G0에서 즉시 중단하는 상황

- 잘못된 JSON, 누락 필드, 부적합한 타입, 미완성 응답.
- 발주량이 유한한 JSON 숫자가 아니거나, 수학적으로 정수가 아니거나, 허용 범위 밖인 경우. 문자열 `"10"`, 소수 `10.5`, 음수, 상한 초과, `true`, NaN/Infinity는 허용하지 않습니다. `10.0` 또는 `1e1`처럼 값이 정확히 정수인 숫자는 허용하고 손실 없이 `10`으로 저장합니다. 이는 반올림·범위 제한에 의한 수량 보정이 아닙니다. 원래 숫자는 `Q_final_raw`에 남습니다.
- timeout, 재시도 가능한 HTTP 오류, 연결 오류, 불완전 HTTP 읽기 등 복구 가능한 호출 오류.

각 논리 호출에서 물리적 API 시도는 최대 1회입니다. 실패한 주문은 실행하지 않고, 이미 그 전에 수행한 입고·출고 상태와 마지막 정상 주문 기록은 진단용으로 남깁니다. 추가 발주·대체 주문·같은 호출 재시도·다음 에이전트 판단은 진행하지 않습니다.

공통 API 설정의 `max_retries=1`은 다른 조건을 위해 유지합니다. N0-G0 호출은 이를 0으로 개별 지정하며, 계획 출력의 `recovery`와 호출 로그의 `effective_max_retries=0`에서 실제 적용값을 확인할 수 있습니다. 조건마다 공유 설정 객체를 수정하지 않습니다.

중단 단위는 **한 조건 × 한 seed 에피소드**입니다. 같은 배치의 다른 독립 에피소드는 계속 진행됩니다. 한 에피소드의 실험적 중단 횟수는 0 또는 1이고, 여러 seed에서 이를 합산합니다. `--resume`으로 중단된 에피소드를 다시 실행하거나 중복 집계하지 않습니다. 새로운 독립 반복을 원하면 새 폴더에 실행하세요.

API 키 오류, 비허용 모델/provider 경로, 예산 초과, 예기치 않은 코드 오류는 실험적 G0 실패와 구분합니다. 이 경우에는 기존처럼 배치를 중단하고 `unexpected_errors` 등에 기록합니다. 연결 오류와 잘못된 모델 출력도 원인을 구분하므로 모두 LLM의 추론 실패라고 해석하지 않습니다.

## 4. 중단 결과 파일과 분석

배치 폴더에는 다음을 저장합니다.

| 파일 | 내용 |
|---|---|
| `execution_outcomes.json` | 조건별 예정·완료·실험적 중단·예기치 않은 오류 수와 비율 |
| `execution_outcomes.csv` | 조건별 실행 결과 표 |
| `failures.json`, `failures.csv` | 중단/오류의 조건·seed·발생 기·역할·단계·원인 |
| `batch_status.json` | 전체 완료·중단·종료 상태와 비용 예산 집계 |
| `results.json` | 정상 완료와 실험적 중단 결과를 함께 보존 |

N0-G0가 중단되면 해당 `episodes/N0-G0__cost__seed-.../`에는 다음이 저장됩니다.

- `summary.json`: `complete=false`, `status="aborted"`, `abort_count=1`, `metrics={}`. 정상 100기 성과는 제공하지 않습니다.
- `abort.json` / `failure.json`: 중단 원인, 시점, 역할, 단계, 오류 타입.
- `abort_snapshot.json`: 중단 순간의 물리 상태. 실패 주문이 아직 미확정인 상태일 수 있으며 재개용이 아닙니다.
- `partial_periods.json` / `.csv`: 중단 전에 확정한 평가기간 에이전트 기록만 보관합니다.
- `partial_metrics`: 부분 실현 비용·비용 구성·완료한 기 수·확정 에이전트 의사결정 수·토큰/호출/API 비용. 준비기간 비용과 미확정 단계의 비용은 합치지 않습니다.
- `api_calls.jsonl` 또는 `mock_calls.json`: 최초 실패 응답/오류를 포함한 실제 시도 기록.

**중간에 멈춰 비용이 적게 누적된 실행을 저비용 성과로 비교하지 않습니다.** 완료율·중단 횟수·중단 원인·실패까지의 기간을 먼저 보고하고, 정상 완료한 에피소드의 비용을 비교할 때는 완료 조건부 결과라는 점을 함께 밝혀야 합니다. 정상 완료만 남기는 선택 때문에 편향이 생길 수 있습니다.

`experiment_abort_rate`의 분모는 **정상 완료 + 실험적 중단**입니다. API 키·예산·프로그램 문제 등으로 판단이 끝나지 않은 실행은 이 비율에 넣지 않고 별도 오류 수로 보고합니다. `abort_rate` 등 기존 호환 필드의 분모는 오류 종료까지 포함하는 `attempted`이므로, `rate_denominators`의 정의를 확인하세요. 전체 예정 실행 수와 미해결 수를 함께 보고해야 합니다.

`batch_status.json`의 `terminal=true`와 `all_trials_terminal=true`는 모든 예정 실행이 정상 완료 또는 실험적 중단으로 끝났다는 뜻입니다. 모두 정상 완료한 경우에만 `complete=true`입니다. 실험적 중단을 포함해 모든 결과를 정상 저장한 배치는 프로세스 종료 코드 0을 반환하고, 예기치 않은 배치 오류는 기존처럼 실패 코드로 끝납니다. 자동화에서 프로세스 코드만으로 에피소드 완료율을 판단하지 마세요.

기존 보조 비용 분석기는 중단 결과를 정상 성과에 자동 포함하지 않습니다. `result_io.py`는 완료된 N0도 읽을 수 있지만 중단 결과가 섞이면 오류를 내어 먼저 실패 표를 확인하도록 합니다. 기존 `run.py analyze`는 과거 파일럿 전용이므로 새 조건의 통계 분석에 사용하지 않습니다.

## 5. 실행 예시

프로젝트 폴더에서 실행합니다. 아래 계획 명령의 `--dry-run`을 제거해야 실제 API를 호출합니다.

```powershell
# 추가 조건과 수정 M2를 선택해 계획 확인
python run_final.py --conditions A N0 N0-G0 C0M2T2 C3M2T2 --seeds 201 --safety-stock 10 --backend openrouter --workers 5 --budget-usd 20 --output results/m2_n0_seed201 --dry-run

# 무료 동작 점검 (LLM 성능 실험이 아님)
python run_final.py --conditions A N0 N0-G0 C0M2T2 C3M2T2 --seeds 201 --safety-stock 10 --backend mock --evaluation-periods 2 --output results/m2_n0_mock_seed201

# 저장된 종료 결과 확인
python status.py results/m2_n0_mock_seed201

# 전체 105조건을 명시적으로 선택
$scmConditions = @((Get-Content ./configs/registered_conditions.json -Raw | ConvertFrom-Json).id)
python run_final.py --conditions $scmConditions --seeds 201 --safety-stock 10 --backend openrouter --workers 16 --budget-usd 20 --output results/m2_n0_all105_seed201 --dry-run
```

seed는 실행 시 직접 지정하며 코드에서 특정 범위로 고정하지 않습니다. API 상한은 해당 실행의 배치 전체 한도입니다. 과거 seed201 폴더에는 이어 쓰지 말고 새 폴더를 선택하세요. 기존 결과·frozen_code·원본 프로젝트와 GitHub는 이 변경으로 수정하지 않았습니다.
